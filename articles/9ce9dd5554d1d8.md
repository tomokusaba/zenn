## はじめに

Microsoft Ignite 2026 で私が強く感じたのは、AI エージェントの競争軸が「どのモデルが賢いか」から、**業務データやシステムにつなぎ、責任を持って本番運用できるか**へ移りつつあることです。

Book of News だけを追うと、モデルや製品の一覧に見えてしまいます。そこでこの記事では、発表を本番エージェントの設計判断として読み替えます。対象は、クラウド／.NET／アプリ開発者と、プラットフォーム・運用担当者です。主な一次情報は [Book of News](https://news.microsoft.com/events/ignite/2026/book-of-news/) と [Ignite overview](https://news.microsoft.com/source/2026/11/17/microsoft-ignite-2026-empowering-human-ambition-intelligence-and-trust/)です。可用性は2026-11-18 時点で確認しています🚀

この記事の中心仮説は、Copilot の価値の置きどころが、**個人ごとの設定や文脈を整えるだけの段階から、組織が持つ知識を管理可能な資産として公開・統制・再利用する段階**へ広がっているという読みです。これは個人設定が不要になったという意味ではありません。個人の作業文脈を入口にしつつ、その上へ組織共通のデータ、スキル、ツール、ポリシー、監査を重ねる設計だと捉えます。

## 今回のゴール

発表を開発者への影響度順に整理し、可用性、責任境界、書き込み権限、再現性、価格、IaC ドリフト、ロックインを判断できるようにします。

### 影響度の順位は何を基準にしたか

発表の規模ではなく、開発者が変更する設計の広さで順位を付けました。

1. runtime、session、tool、identity、data の責任境界が変わるか
2. GA か、preview／Frontier を隔離して進められるか
3. 業務データや既存システムへ安全につながるか
4. monitoring、approval、rollback、cost management まで変更するか

この基準では、Foundry／harness を実行基盤の第1群、GitHub Copilot の Fusion／Projects／app／MAI を開発体験の群、IQ を組織context基盤として捉えます。各製品の番号は、群としての重要度ではなく、それぞれの設計変更の広さで付けています。

## 全体像: 個人の文脈から組織知識の本番運用へ

モデルだけを選ぶのではなく、**contextを渡し、toolの副作用を制御し、identityとactivityを追跡し、改善を配布する**設計へ移ります。これは「モデル実験から本番運用へ」という変化と同時に、「個人向けの便利さから、組織知識のライフサイクル管理へ」責任範囲が広がる変化でもあります。

Book of News が示す Microsoft IQ は、業務データや組織のノウハウを再利用する企業コンテキスト基盤（enterprise context platform）です。Copilot harness はそのcontextを使ってagentを動かし、Agent 365 と Entra Agent ID は、agent、tool、権限、activity、costを組織として見えるようにします。これは公式発表を本記事の設計判断へ読み替えたもので、製品間の正式な責任境界を示す仕様ではありません。MCP は接続点です。ただし、これらが個人のprofile、memory、preferenceを置き換えるとまでは書かれていません。個人contextと組織contextの境界を設計する段階へ進んだと読むのが妥当です。

Preview や Frontier では、契約・テナント・リージョンの確認も必要です。

## 1位: Microsoft Foundry + Copilot harness

Foundryは、multi-turn evaluation、production trace、失敗分析、Agent Optimizer、model trainingを一つの改善ループにしました。作って終わりではなく、本番信号から次の改善案を作り、評価して配布する段階です。

Copilot SDK 2.0は、本番で使われるnative Rust runtimeのハーネスをアプリへ組み込み、6言語をサポートします。ハーネスはモデルとアプリの間で、モデル呼び出し、途中状態、tool実行、失敗時の進行を制御します。[Harnesses in Copilot Studio](https://learn.microsoft.com/en-us/microsoft-copilot-studio/harnesses-overview?WT.mc_id=DT-MVP-5004827)も、harness の違いが実行方法や billing に影響するケースを説明しています。

### Copilot SDK 1.0から2.0で何が変わるのか

1.0系がGA（一般提供）になった段階では、すでにplanning、tool invocation、file edit、streaming、multi-turn sessionをアプリへ組み込めました。6言語、custom tools／MCP、system prompt customization、OpenTelemetry、OAuth／BYOK、remote session、hookも提供されていました。したがって、「ハーネスがない版」だったわけではありません。[1.0 GA release](https://github.blog/changelog/2026-06-02-copilot-sdk-is-now-generally-available/)は当時の提供範囲を確認できます。2.0の大きな変化は、**runtimeをどのように切り出し、複数sessionを隔離・再利用するか**というhosting modelです。[Copilot SDK 2.0の公式解説](https://commandline.microsoft.com/microsoft-copilot-sdk-2-0-github/)と[SDK repository](https://github.com/microsoft/copilot-sdk)を基に整理すると、次の違いがあります。

| 観点 | 1.0系 | 2.0 |
|------|-------|-----|
| 🏷️ 名称と位置づけ | GitHub Copilot SDKとしてGA。Copilot CLIのagent runtimeへprogrammaticに接続 | Microsoft Copilot SDK。Microsoft／GitHubで共用するCopilot harnessのprogramming interfaceへ |
| 🧱 runtime | 強い境界を要するsessionではcontainerを使う構成が主な選択肢だった | native Rust runtimeを既定でin-process実行。child process、standalone serverも選択できる |
| 👥 session model | session APIとmulti-client supportはあるが、session分離のinfra負担はhost設計へ表れやすい | 1 runtime processで多数のsessionを持ち、state、credential、tools、files、historyをsessionごとに分離 |
| 🪪 identity | runtimeを起動したprocess identityに実行権限が寄りやすい | session作成時にuser tokenまたは短命token providerを渡し、model／tool callをsession identityへ紐付け可能 |
| 🗂️ filesystem / durability | container lifetimeとsession lifetimeを分離しにくい | session journalとsessionFsでstateをprocess外へ保存し、別instanceからresumeできる |
| 🔧 tool boundary | custom tools、MCP、hook、allow／denyは利用可能 | `mode: "empty"`でambient shell／file／default toolを持たず、host-owned toolをsession単位のallow listで追加 |
| ⚙️ performance | container／process起動をsessionごとに伴う場合、そのoverheadが必要になる | 公式のwarm workload測定ではTypeScript CLIからin-process Rust coreへ変え、client＋session＋1 turnが5.25秒から55.3ms、10 clientのmemoryが1,383MBから126MB。再現条件は公式記事に限定され、実環境では再計測が必要 |

API 利用者から見ると、2.0では軽い共有runtimeで始め、必要なときだけsandboxへ寄せる選択肢が増えます。たとえば、質問回答はshared runtime、コード実行はisolated sandbox、長時間処理はsession journalを外部storageへ保存、という分割です。Foundryで評価・観測したagentを、自前アプリの入口やSaaSのmulti-tenant backendへ組み込む場面に直接影響します。

責任境界も変わります。container-per-sessionではOS boundaryがshellやfileを守りやすかった一方、shared runtimeでは、**tenant隔離、credential選択、tool allow list、storage分離に関するhost application側の責任が増えます**。SDK 2.0のRust runtimeがin-processで高速でも、単体でsandboxやcrash isolationを提供するわけではありません。信頼できないcodeを実行する場合はchild process、VM、containerとの組み合わせを選びます。

移行時は、次の点を実装判断として確認します。

- package／namespaceがGitHub名からMicrosoft名へ移行する途中でもあるため、採用する言語ごとの現在のpackage名とimport pathを確認する
- `RuntimeConnection`やin-process／spawned／TCPのhosting選択を明示し、crash isolationを失っていないか確認する
- 従来のambient accessを継承せず、`mode: "empty"`から必要なfile、shell、MCP toolだけを許可する
- static tokenからshort-lived token providerへ移し、session ownerと再開時のauthorizationを再検証する
- `sessionId`だけでresumeせず、tenantとcallerがそのsessionを所有することを確認する
- session journalの保管先、暗号化、retention、PII、deleteを規約として決める
- benchmark値を目標値として転記せず、自分のsession concurrency、model、tool latencyでload testする

:::message alert
2.0への移行は「package更新」ではなく、**execution placement、identity、persistence、isolationの再設計**です。特に既存アプリを共有runtimeへ一本化する場合、write toolを追加する前にread-only tenant isolation testを通してください。
:::

- 開発者への影響: promptだけでなく、成功条件、許可tool、retry、承認、telemetry、evaluation dataを版管理する必要があります。
- 向く場面: 複数工程の業務処理、ファイル操作、複数toolの利用、継続改善が必要なagent。
- 注意: 単純な決定的処理は通常のworkflowの方が安定します。改善案も人が承認するまで自動配布しないでください。

Agent OptimizerなどはGAです。一方、human annotation、Managed Training、Programmed Trainingはpreviewです。SDK 2.0もGAですが、利用する下位機能単位で仕様を確認します。

実行基盤の次に、開発者が毎日触れるGitHub Copilotの作業面とモデル選択を見ます。

## 2位: GitHub Copilot Fusion

Fusion自体は [GitHub Universe 2026](https://github.blog/news-insights/company-news/github-universe-2026-evolving-every-layer-of-the-stack/) で先に紹介されました。Ignite 2026では、利用surface、新しいmodel、Terminal-Bench 4.1の結果が追加発表されています。

[GitHubのIgnite更新](https://github.blog/changelog/2026-11-17-github-copilot-fusion-updates-more-availability-benchmarks-and-models/)では、Copilot Fusionがgithub.com、Visual Studio、GitHub Mobile betaで選択可能になり、MaxにClaude Sonnet 5.5、HighにGPT-6.1 Terra、StandardにMAI-Code-2が加わりました。Fusionはtaskに応じてmodelを選び、複数modelを組み合わせる仕組みです。

:::message
Universe との差: Fusion自体と「taskごとにmodelを組み合わせる」という考え方は、[GitHub Universe 2026](https://github.blog/news-insights/company-news/github-universe-2026-evolving-every-layer-of-the-stack/)ですでに紹介されていました。Igniteでは、利用surfaceの拡大、新たに加わったmodel、Terminal-Bench 4.1の結果という追加情報が公開されています。
:::

- 従来との差: model pickerで1つを選んで全工程へ使うのではなく、reasoning、coding、debugging、tool useに応じて構成を調整します。
- 開発フローへの影響: 「どのmodelを使うか」から、「effort、cost、task typeの目標をどう固定するか」へ設計点が移ります。
- 向く場面: issueの調査から実装、test、reviewまで工程が混在し、単一modelの固定選択では品質か費用のどちらかを犠牲にしやすい作業。
- 慎重に判断すべき点: [Fusionの公開ベンチマーク](https://github.blog/changelog/2026-11-17-github-copilot-fusion-updates-more-availability-benchmarks-and-models/)はTerminal-Bench 4.1でMaxが71.2%という結果ですが、**自社のrepository、tool、評価基準では再現されるとは限りません**。model／provider policy、使用量課金、監査可能なtask traceも確認します。

## 3位: GitHub Copilot Projects

[Copilot Projects](https://github.blog/changelog/2026-10-28-github-copilot-app-universe-releases/)は、複数repository、design、Slack thread、meeting noteなどのcontextとagent sessionを一つのprojectにまとめ、完了したPRなどをreviewへ戻すpublic previewです。

:::message
Universe との差: Copilot ProjectsはGitHub Universeで導入・public preview化が先に発表されており、GitHub Universe 2026のまとめでも中核機能として掲載されています。IgniteのBook of Newsがプロジェクト名を新規発表したわけではなく、GitHub Copilotを組織展開する文脈で読むための既存の開発面です。
:::

- 従来との差: 単一repositoryのchatやsessionを人が連結するのではなく、goal、context、parallel sessions、resultの確認場所を一つにします。
- 開発フローへの影響: task分解、branch conflict、review担当、承認順序をprojectの管理単位として扱えます。
- 向く場面: cross-repo migration、designから複数PRへの実装、issue triageなど、document／code／外部toolのhandoffが多い作業。
- 慎重に判断すべき点: projectはpublic previewです。共有contextの権限、外部資料の持ち込み、agent間の競合、結果のownership、project削除時のretentionを先に定めます。

## 4位: GitHub Copilot app

[GitHub Copilot appのIgnite更新](https://github.blog/changelog/2026-11-17-github-copilot-app-microsoft-ignite-releases/)ではAzure DevOps repository対応がpublic previewになり、branch作成、変更、PR、review修正、agent mergeまでを一つのappで扱えます。GitHub Enterprise Server対応はGAです。browser useはChromiumベースブラウザーへpublic previewで導入され、isolated tab groupで動作し、既定では無効です。

Copilot app自体とagent-firstな開発面はUniverseですでに紹介されていました。一方、Azure DevOpsへの統合、browser use、GitHub Enterprise ServerのGAは、GitHubがIgnite日に発表した個別更新として扱います。Universeの基盤面に対し、IgniteではMicrosoft環境や既存enterprise estateへ開発者体験を広げる新要素が加わったと整理できます。

- 開発フローへの影響: GitHub Copilot appからAzure DevOpsのrepositoryも扱えるようになり、既存のMicrosoft開発環境へ開発者体験が広がります。ログイン済みbrowserでの操作もpublic previewへ追加されました。
- 向く場面: repository間をまたぐ修正、ブラウザーで必要なE2E test、review commentの反復修正。
- 慎重に判断すべき点: Azure DevOpsのcloud sessionは利用できません。browser useは画面操作を実行するため、credential、download、外部送信、PIIをpermission設計とisolated environmentで制限します。

## 5位: MAI-Code-2 / MAI-Code-2-Flash

新しいcoding modelとして、[MAI Code 2とMAI Code 2 Flash](https://github.blog/changelog/2026-11-17-mai-code-2-and-mai-code-2-flash-in-github-copilot/)がGitHub Copilotで提供されています。MAI Code 2はcomplex task向け、Flashは日常のtargeted edit／routine fix／rapid iteration向けです。両方ともagentic coding workflow向けのusage-based billingです。

この2モデルはBook of NewsとIgnite日にGitHubが発表した新モデルです。Universeで扱われていたFusionやProjectsとは異なり、MAI-Code-2／FlashそのもののGitHub Copilot提供はIgniteの発表内容として扱います。

- 従来との差: MicrosoftのMAI modelをGitHub Copilotの対応surfaceで選べ、Fusion StandardはMAI-Code-2も候補にします。surfaceごとの対応と管理設定は、プランおよびリリース時点の公式一覧で確認します。
- 提供状況: MAI Code 2はCopilot Pro、Pro+、Max、Business、Enterprise。FlashはFree、Studentを含む複数planです。Enterprise／Business管理者はmodel policyで制御できます。Book of Newsでは両モデルはGitHubでGA、FoundryのCode-2-Flashはprivate previewです。
- 採用に向くケース: MAI Code 2はdeep debugging、multi-file refactoring、repository-wide reasoning。Flashは小さな修正や高頻度の支援です。
- 慎重に判断すべき点: 組織のmodel policyが自動的に新modelを有効にする設定か、BYOKやdata boundaryをどう扱うか、実作業でのcost per successful taskを測ります。画像生成のMAI-Image-2.7／2.7-FlashとMAI-Cyber-2-Flashはcodingの選択肢とは別用途で、公式情報ではpreview／MDASH限定です。

### 名前が似ている製品の責任境界

| 名称 | 主な責任 | 判断するowner |
|------|----------|---------------|
| 🧭 Copilot Fusion | taskごとのmodel／effort orchestration | 開発者、Copilot管理者 |
| 📁 Copilot Projects | goal、context、複数session／repositoryの成果 | 開発者、project owner |
| 🧠 Microsoft Copilot harness / SDK 2.0 | agent loop、tool、session、persistence | app／platform開発者 |
| 🤖 Foundry Agent Service | Foundry上のagent build、runtime、evaluation、enterprise connection | AI／application platform team |
| 📊 Agent 365 | agent・tool・cost・activity・riskのorganization governance | IT／security／business owner |

この整理では、Fusionが「どうmodelを組み合わせるか」、Projectsが「どのworkを集めるか」、harness／SDKが「agentをどう実行するか」、Agent 365が「organizationとしてどう統制するか」を担います。ここまでをまとめると、GitHub Copilotの更新は単なるeditor機能ではなく、開発活動そのものを組織知識・権限・監査へつなぐ入口です。

## 6位: Microsoft IQ

Microsoft IQは、Work IQ、Fabric IQ、Foundry IQ、Web IQをまとめるenterprise context platformです。仕事、業務データ、文書、Web情報を、agentが再利用できるcontextとして管理します。

以前は接続先ごとにRAGやpermission伝播を実装しがちでした。IQは、semantic modelやbusiness pluginなどを横断的に再利用し、組織固有の知識を資産として残すことを狙います。

ここが「個人のCopilot設定」からの広がりです。個人のプロファイルや会話に閉じたコンテキストに加え、誰が利用できる業務定義か、どの情報源がauthoritativeか、誰がスキルを公開・更新・廃止するかを、組織の資産として管理できる方向です。Book of Newsでは、business pluginがscenarioごとのguidanceを階層化し、sensitivity label、change audit、governance insightを伴うと説明されています。個人設定を管理者が中央化して置き換えるのではなく、**個人のコンテキストと組織で承認したコンテキストを接続する**ものとして設計する必要があります。

設計対象は「検索できるか」から、誰の権限で見えるか、業務指標の定義はどこか、根拠と鮮度をどう示すかへ広がります。Microsoft 365やFabricの既存権限・semantic modelを利用できる点は大きいです。

- 開発者への影響: prompt内だけでcontextを組み立てず、公開済みbusiness plugin、semantic model、source権限、citationをapplication設計へ組み込みます。
- 向く場面: 規程・契約書の横断支援、営業文脈とERP／Power BIを組み合わせた判断、組織内business plugin。
- 注意: source削除やaccess拒否の反映、citation、stale context、token costを評価します。

Microsoft IQ、context capability、building blocksはGAです。business pluginはFrontier、Foundry IQのknowledge graphやretrieverなど一部機能はpreviewです。

## 7位: Model Context Protocol（MCP）

MCPは、エージェントと外部tool・dataをつなぐ共通仕様です。[Work IQ MCP overview](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/work-iq/mcp/overview?WT.mc_id=DT-MVP-5004827)は、Microsoft 365 entityへのread/create/update/delete、action実行を単一endpointで提供すると説明しています。`retrieve`はpublic previewです。

[Foundry MCP tool](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol?WT.mc_id=DT-MVP-5004827)ではremote MCP serverをagentへ接続できます。独自pluginごとの接続から共通化できる反面、MCPだけでは安全性は保証されません。

| 観点 | 実装ポイント |
|------|--------------|
| 🔍 discovery | toolをallow listで管理する |
| ✍️ write | 人の承認、冪等性キー、再試行上限を持つ |
| 🔐 authorization | 人・agent・serviceの権限を区別する |
| 🧾 audit | tool名、引数、結果、承認者を残す |
| 🧯 failure | timeout、partial failure、compensationを想定する |

- 向く場面: Microsoft 365、ticket、monitoring、DBを複数agentから利用。
- 注意: delete、mail送信などの副作用toolはread toolと権限を分けます。

Microsoft Entra MCP Server for EnterpriseはGAです。Agent 365のMCP gateway/local agent governance、MCP Firewallはpreviewです。

## 8位: Entra Agent ID + Agent 365

書き込みを伴うagentには、人とは別のidentity、owner、停止手順が必要です。[Microsoft Entra Agent ID](https://learn.microsoft.com/en-us/entra/agent-id/?WT.mc_id=DT-MVP-5004827)は、agent identityの管理、governance、resource保護を扱います。Agent 365はそのidentityを基礎に、inventory、risk、tool、cost、activityをcontrol planeとしてまとめます。

IQで組織知識を公開できても、それだけでは誰がどのagentに何を使わせるかは決まりません。Agent 365のMCP server／tool governance、plugin／skill governance、usage／activity insightは、その公開範囲と利用状況を管理する側です。Copilot harnessはagentの実行、IQはcontext、Agent 365は可視化・統制、Entra Agent IDはagentのidentityという責任分担になります。

共有service accountから、agent別identity、owner、permission、activity logへ移すことが重要です。ここでは深いOAuth設計には踏み込みませんが、**モデルの安全性と、そのagentが持つ権限は別物**です。

- 向く場面: 複数チームでagentが増える組織、顧客データを書き換える自動化、長時間動くagent。
- 注意: inactive agent、owner変更、退職、緊急停止、license条件を運用手順へ入れます。

Igniteでのdiscovered local agent / Microsoft cloud agent向けAgent ID、Dynamic Agent Risk、classificationはpreviewです。Agent 365のusage/activity insight、plugin/skill governanceはGA、action centerは12月予定のprivate previewです。

本記事では、Entra Agent ID を Ignite 全体の identity・governance 基盤として位置づけることに留めています。認証・認可の詳細は、公開案内がある [.NET ラボ勉強会 2026 年 12 月](https://dotnetlab.connpass.com/event/408209/) で松崎 剛さんが予定している「Deep dive into Microsoft Entra Agent Identity」へ譲ります。2026 年 12 月 19 日に開催予定で、会場、オンライン配信、参加登録については案内ページを参照してください。

## 9位: Azure Catalyst + GitHub Copilot modernization

Azure Catalystは、estate discovery、migration planning、modernization、executionをつなぐGA experienceです。GitHub Copilot modernizationは、.NET、Java、C++のupgrade、migration、CLI assessmentを扱います。[Modernization overview](https://learn.microsoft.com/azure/developer/github-copilot-app-modernization/overview?WT.mc_id=DT-MVP-5004827)では、IDEとCLIの役割と、人によるレビュー・検証が示されています。

- 開発者への影響: framework、dependency、container、IaCの変更を一つのplanにできます。
- 向く場面: 大規模portfolio、app/database/networkをまたぐ移行、migration patternの共通化。
- 注意: build、integration test、performance、rollbackを必ず検証します。生成IaCとportal変更のdriftも検知してください。

Catalyst本体と主要GitHub Copilot modernization experienceはGA、統合app/database modernizationやBizTalk移行などの追加機能はpreviewです。

## 10位: Azureのagentic operations

Azure Monitor、Azure Copilot、Azure SRE Agentにagentic capabilityが追加されました。SRE Agentはalert、trace、deployment、ticket、repositoryをつなぎ、原因候補や対応案を提示します。

[Azure SRE Agent overview](https://learn.microsoft.com/en-us/azure/sre-agent/overview?WT.mc_id=DT-MVP-5004827)では、run mode、managed identity、RBAC、tool単位のallow/ask/deny、Bicep、auditが扱われています。

運用agentは、read-only investigation → ticket更新 → 限定write → autonomousの順で広げます。

- 向く場面: 頻出障害のtriage、deploymentとの相関、runbook候補化。
- 注意: restartやscaleにも緊急停止、承認者、変更上限、冪等性を設けます。

Azure Monitor natural languageとhealth modelはGA、Copilot spaces/custom skillsとSRE Agent新機能はpreview、Oracle/SAP workload拡張はprivate previewです。

## 11位: HorizonDB + Fabric HorizonDB + Fabric apps

Azure HorizonDBはmission-critical向けPostgreSQL互換DBとしてGAです。Entra認証、private endpoint、managed identity、encryption、multi-zone resilienceを備えます。

[Fabric HorizonDB overview](https://learn.microsoft.com/en-us/fabric/database/horizondb/overview?WT.mc_id=DT-MVP-5004827)はserverless PostgreSQLとしてpreview提供を示し、pause/resume、mirroring、region・capacity制約を説明しています。[Fabric apps overview](https://learn.microsoft.com/en-us/fabric/apps/overview?WT.mc_id=DT-MVP-5004827)は、TypeScript data modelからAPI、認証、hosting、GraphQL endpointを生成するmanaged backendです。

- 向く場面: 社内tracking、dashboard、短命なagent-generated app、transactional dataとFabric analyticsの連携。
- 開発者への影響: backendの初期構築を減らせます。一方、Fabric HorizonDBのpreviewではcreator identityだけの接続など制約があります。
- 注意: scale-to-zeroの再接続、mirroringの遅延、backup/restore、pricing、extension差をsynthetic dataで確認します。

Fabric apps/RayfinはGAです。Azure HorizonDBのAI model management / AI Functions / PipelinesとFabric HorizonDBはpreviewです。

## 12位: Windowsのlocal / hybrid AI

Windowsは、PC、Cloud PC、server、Azureのどこで推論・実行するかを選ぶhybrid intelligenceを強調しました。[Windows Ignite blog](https://blogs.windows.com/windowsexperience/2026/11/17/microsoft-ignite-2026-building-windows-for-the-next-era-of-work/)ではlocal routing、containment、identity、Windows 365 for Agents、Windows Server 2028が説明されています。

- 向く場面: sensitive local data、coding支援、APIのないlegacy Windows appのcomputer-use。
- 開発者への影響: latency、data residency、offline、token costを改善できる可能性があります。
- 注意: 端末、driver、GPU/NPU、memoryで結果が変わるため、cloud fallbackを含む共通評価が必要です。

MXCはGA、GitHub Copilot hybrid/local routingとprocess container改善はpreviewです。Windows Server 2028はpublic preview、hybrid intelligence機能の限定提供はearly accessです。

## 責任分担と導入チェック

managed serviceでもアプリチームの責任はなくなりません。

| レイヤー | Platform / Security | Application team | 共同で決めること |
|----------|---------------------|------------------|------------------|
| 🧠 model | 提供・quota・基盤監視 | prompt・fallback | quality/latency/cost SLO |
| 🗂️ context | connector・classification・公開policy | source・grounding・UX | retention・citation・個人／組織context境界 |
| 🔧 tool | registration・gateway・secret | validation・冪等性 | read/write・approval |
| 🔐 identity | lifecycle・policy | least privilege・owner | 廃止・緊急停止 |
| 📊 observability | 統合log・保管 | task trace・evaluation | PII・retention |
| 🏗️ release | landing zone・policy | app config・rollback | IaC drift・change control |

導入前に、次を確認しておくとよいです。

- [ ] agent、tool server、業務systemのownerは誰か
- [ ] 個人contextと組織contextの公開範囲、継承、失効を分けて定義したか
- [ ] IQのskill／pluginを誰が承認・公開・更新・廃止するか
- [ ] read-onlyから始め、write actionごとに承認するか
- [ ] prompt、model、schema、context snapshot、evaluation dataを固定できるか
- [ ] tool call、引数、結果、承認、最終変更を監査できるか
- [ ] timeout、partial success、retry、human handoffを試験したか
- [ ] portal変更とIaCのdriftを検知するか
- [ ] preview停止時の代替と、lock-inからのexit strategyがあるか
- [ ] token、hosting、DB、observabilityの価格を試算したか
- [ ] local/Cloud PC/serverのhardware差を再現試験したか

## まとめ

Ignite 2026の中心は、**model + context + tools + identity + operations**を一つのproduction systemとして扱う方向です。分析上は、個人向けCopilotを組織知識のcontrol planeで置き換えるのではなく、個人の設定や文脈を生かしたまま、組織のデータ、skill、policy、権限、監査を再利用可能な資産へ引き上げる変化と読めます。

Foundry／harnessは実行と改善、GitHub CopilotのFusion／Projects／MAIは開発活動、IQは組織context、MCPは接続、Agent ID／Agent 365は統制、SRE Agentは運用actionを担います。

私なら、まずGitHub CopilotのProjectsで小さなcross-repo task、Fusionで同じtask setを評価し、model・cost・review負荷を測ります。並行してread-onlyで一つの業務flowを選び、組織contextの公開範囲、評価、traceを固定します。次にwriteをaction単位で許可し、GAから始めてpreviewは差し替え可能なadapterとして隔離します。価格、reproducibility、vendor lock-inもPoC開始時にexit conditionとして決めておきましょう。

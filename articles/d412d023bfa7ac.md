## はじめに

.NET 11 が、2026 年 11 月 10 日に正式リリースされました！ 🎉

今回も更新は言語だけではありません。ランタイム、SDK、ASP.NET Core、EF Core、Windows Forms、WPF まで、アプリケーションを支える各層に変更が入っています。

この記事では、.NET 10 からの主な更新をトピック別に整理します。特に C# 15 の **Union（共用体）** は、書きやすさだけでなく、値型を格納したときのボックス化まで掘り下げます。

Union は重要な更新ですが、私は手放しでは歓迎していません。**既定の `union` 宣言で値型ケースがボックス化される**設計を踏まえると、ライブラリーではなく言語機能として導入する価値を、まだ十分に見いだせていません。

:::

## C# 15 ― 型の表現力が広がる

C# 15 は、`net11.0` を対象とするプロジェクトの既定の言語バージョンです。通常の新機能を使うために、すべてのプロジェクトへ `LangVersion=preview` を設定する必要はありません。

| 機能 | 何が変わるか |
|---|---|
| 🔀 Union types | 複数のケース型のいずれかを持つ型を宣言できる |
| 🔒 Closed hierarchies | `closed` で直接の派生型を同一アセンブリ内に制限できる |
| 📦 Collection expression arguments | `[with(capacity: 100), .. values]` のようにコレクション式へ構築時の引数を渡せる |
| 🧩 Extension indexers | 拡張ブロックでインデクサーを定義できる |
| 🔁 ラベル付き `break` / `continue` | 入れ子のループで、どのループを抜ける・継続するかを指定できる |
| 🔧 古いランタイムへの対応拡大 | 非 virtual な static インターフェイスメンバーを、既定のインターフェイス実装に非対応のランタイムでも利用できる |

一方、**memory safety 関連の機能はプレビュー**です。通常の C# 15 の機能と同列に「すべて正式対応」とまとめないようにしましょう。

## Union ― 重要な更新だが、既定の設計には疑問

### 通常の宣言は `object?` を使って値を保持する

例えば、「整数または真偽値」を持つ型を次のように宣言できます。

```csharp
public union NumberOrFlag(int, bool);
```

この宣言から生成される Union は struct ですが、中身の保持には `object?` を使います。

```csharp
NumberOrFlag number = 42; // int の値をボックス化して格納する
NumberOrFlag flag = true; // bool の値をボックス化して格納する
```

**ボックス化（boxing）**は、値型の値を `object` などの参照型として扱えるようにする変換です。ヒープへの割り当てが残る場合は、その後の GC（ガベージコレクション）の負荷にもつながります。

公式リファレンスでも、通常の `union` 宣言について「値型ケースを常にボックス化し、内容を `object?` として保持する」と説明しています。Roslyn のテストでも、`int` を受け取る生成コンストラクターに `box System.Int32` が入ることを確認できます。

私が問題視したいのは、**通常の Union に値型を格納するとボックス化され、使い方によっては値ごとのオブジェクト割り当てにつながる**点です。例えば、小さな解析結果を大量に保持する処理や、頻繁に更新する数値データでは無視できません。

ただし、次の違いは整理しておく必要があります。

| 場面 | ボックス化の考え方 |
|---|---|
| 🔢 通常の Union に `int` / `bool` を格納する | 値型のケースをボックス化する |
| 🧵 通常の Union に参照型のケースを格納する | この格納に伴う値型ケースのボックス化はない |
| 📖 通常の Union の `.Value` を読む | 格納済みの参照を返す。読み出すたびに同じケースを再ボックス化するわけではない |
| 📦 Union 自体を `object` / `IUnion` に変換する | Union の struct 自体を別途ボックス化し得る |

また、IL（中間言語）に `box` があることと、最適化後も必ずヒープ割り当てが残ることは同義ではありません。JIT の最適化で除去される場合もあります。「どんな使い方でも必ず割り当てが発生する」とは断定せず、実際の保持方法に近い条件で測ります。

出典：[union リファレンス](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/builtin-types/union?WT.mc_id=DT-MVP-5004827)、[Union の言語仕様案](https://github.com/dotnet/csharplang/blob/68b7855d1189437a6ca4e6ee948f70c5afb7833c/proposals/csharp-15.0/unions.md)、[Roslyn の Union テスト](https://github.com/dotnet/roslyn/blob/9376c7a1acae1540a0ce496b8c1825fe73119cc5/src/Compilers/CSharp/Test/CSharp15/UnionsTests.cs)、[JIT によるボックス化除去の解説](https://devblogs.microsoft.com/dotnet/performance-improvements-in-net-10/?WT.mc_id=DT-MVP-5004827)

### 回避には「型付きの保持」と「型付きの取り出し」の両方が必要

対策は、単に `TryGetValue` というメソッドを追加することではありません。コンストラクターが既に `object` へ格納していたら、その時点のボックス化は取り消せません。

C# 15 では、`[Union]` 属性を付けたカスタム struct で、次の構成を用意できます。

- ケース型を受け取る public コンストラクターを持つ
- 値を `object` ではなく型付きフィールドに保持する
- ケース型ごとの `TryGetValue(out ...)` で値を取り出す
- `HasValue` と `object? Value` を提供する

コンパイラーは、対応する型パターンの処理に `TryGetValue` を利用できます。これにより、**格納時とパターンマッチ時の両方で、値を `object` に変換せずに済みます**。

ただし、この方法では型付きの保持と取り出しを自分で用意する必要があります。既定の宣言だけではこの選択ができないことに、私は疑問を感じています。

次の例では、`int` のフィールドとケース識別用の `bool` だけで値を保持します。真偽値のケースは、整数フィールドの `0` / `1` で表現します。

`IUnion` はランタイムとの相互運用のために実装していますが、カスタム Union の言語上の動作に必須ではありません。また、この例の `default(IntOrBool)` は「値なし」ではなく、整数の `0` として扱う設計です。

### ボックス化の差を確認できるサンプル

.NET 11 SDK をインストールし、次のコマンドでコンソールプロジェクトを作成します。

```powershell
dotnet new console -n UnionAllocationDemo -f net11.0
Set-Location UnionAllocationDemo
```

`Program.cs` を次の内容に置き換えてください。このブロックは、比較対象の通常の Union とカスタム Union を含む完全なサンプルです。

```csharp
using System.Runtime.CompilerServices;
using System.Runtime.InteropServices;

IntOrBool integer = 42;
IntOrBool boolean = true;
Console.WriteLine($"int: {Read(integer)}, bool: {Read(boolean)}");

_ = Measure(10_000); // 計測前にウォームアップする。
Console.WriteLine(RuntimeInformation.FrameworkDescription);
Console.WriteLine(RuntimeInformation.ProcessArchitecture);
for (int iteration = 0; iteration < 3; iteration++)
{
    var result = Measure(100_000);
    Console.WriteLine($"normal={result.Normal:N0}, custom={result.Custom:N0}");
}

static int Read(IntOrBool value) => value switch
{
    int number => number,
    bool flag => flag ? 1 : 0,
};

static (long Normal, long Custom) Measure(int count)
{
    // 配列本体の割り当ては計測対象外。
    var normal = new NumberOrFlag[count];
    var custom = new IntOrBool[count];

    long start = GC.GetAllocatedBytesForCurrentThread();
    for (int i = 0; i < count; i++)
        normal[i] = i;
    long normalBytes = GC.GetAllocatedBytesForCurrentThread() - start;

    start = GC.GetAllocatedBytesForCurrentThread();
    for (int i = 0; i < count; i++)
        custom[i] = i;
    long customBytes = GC.GetAllocatedBytesForCurrentThread() - start;

    GC.KeepAlive(normal);
    GC.KeepAlive(custom);
    return (normalBytes, customBytes);
}

public union NumberOrFlag(int, bool);

[Union]
public readonly struct IntOrBool : IUnion
{
    private readonly int _value;
    private readonly bool _isBool;

    public IntOrBool(int value)
        => (_value, _isBool) = (value, false);

    public IntOrBool(bool value)
        => (_value, _isBool) = (value ? 1 : 0, true);

    public object? Value
    {
        get
        {
            if (_isBool)
                return _value != 0;

            return _value;
        }
    }

    public bool HasValue => true;

    public bool TryGetValue(out int value)
    {
        value = _value;
        return !_isBool;
    }

    public bool TryGetValue(out bool value)
    {
        value = _value != 0;
        return _isBool;
    }
}
```

`Read` の型パターンは、カスタム Union の型付き `TryGetValue` を利用します。整数と真偽値のどちらも、`.Value` を経由せずに取り出せます。

Release 構成で、デバッガーを付けずに実行します。

```powershell
dotnet run -c Release
```

Windows x64、SDK 11.0.100、ランタイム .NET 11.0.0 で実行したところ、10 万件を格納する計測区間の結果は次のとおりでした。ウォームアップ後の 3 回とも同じ値でした。

```text
int: 42, bool: 1
.NET 11.0.0
X64
normal=2,400,000, custom=0
normal=2,400,000, custom=0
normal=2,400,000, custom=0
```

これは **配列を事前に確保し、その要素へ整数ケースを格納する間のマネージドヒープ割り当て**です。配列自体のサイズや、アプリケーション全体のメモリ使用量を比べた数値ではありません。値を配列に保持しているため、生成してすぐ捨てるだけの例とも条件が異なります。

`GC.GetAllocatedBytesForCurrentThread()` は現在のスレッドの累積割り当て量を返します。生存オブジェクト量やネイティブメモリは測りません。値は環境や最適化に依存するので、この結果をすべての Union の保証として扱わないでください。

出典：[ボックス化を避けるカスタム Union の公式チュートリアル](https://learn.microsoft.com/en-us/dotnet/csharp/whats-new/tutorials/unions?WT.mc_id=DT-MVP-5004827)、[GC.GetAllocatedBytesForCurrentThread](https://learn.microsoft.com/en-us/dotnet/api/system.gc.getallocatedbytesforcurrentthread?view=net-11.0&WT.mc_id=DT-MVP-5004827)

### `.Value` に戻したら、そこではボックス化する

このカスタム実装も、`.Value` の戻り値は `object?` です。`int` / `bool` を返すときにはボックス化します。Union 自体を `object` やインターフェイスへ変換する経路も、別途確認が必要です。

性能が重要な経路では、具体型のまま型パターンや型付き `TryGetValue` で処理します。ログ出力・汎用 API・非ジェネリックなコレクションなどで、意図せず `object` に戻していないかも確認しましょう。

また、ケースが大きな struct なら、ボックス化を避けてもコピー量や Union 自体のサイズが増えることがあります。こうした負担も含め、**通常の Union を無条件に採用せず、既存ライブラリーやカスタム実装と比較する**ことが重要だと考えています。

### 私見：重要な更新だが、手放しでは歓迎できない

Union が影響の大きい重要な更新であることは認めます。ただし、既定の設計や既存ライブラリーとの差を考えると、**言語機能として入れる価値を十分に見いだせていない**というのが現時点の評価です。

最大の理由は、既定の `union` 宣言が値型ケースをボックス化することです。複数の型のいずれかを表すだけなら、ライブラリーでも実現できます。実際、既存の [OneOf](https://github.com/mcintyre321/OneOf/blob/6e02dbe75d0f20f198c640d4c04190a85c5ac9e6/OneOf/OneOfT1.generated.cs#L6-L25) は `readonly struct` の中にケースごとの型付きフィールドを持ち、値型ケースの格納時にボックス化しません。言語に組み込まれたほうが、既存ライブラリーより割り当ての面で不利になり得ることに、私は違和感があります。

| 観点 | OneOf（ライブラリー） | C# 15 の既定の `union` |
|---|---|---|
| 💾 値型ケースの保持 | ケースごとの型付きフィールドに保持。格納時にボックス化しない | `object?` に保持。値型をボックス化する |
| 📏 struct の構成 | ケースごとのフィールドと識別子を保持 | 参照 1 つを保持 |
| ✅ 全ケースの処理 | `Match` / `Switch` がケースごとのデリゲートを要求する | `switch` 式の網羅性チェック |
| 🔁 ケース型からの変換 | 暗黙の変換演算子 | 言語の Union 変換 |
| 🌐 エコシステムとの連携 | ライブラリーごとに追加対応が必要な場合がある | System.Text.Json や OpenAPI が Union を認識する |

なお、`OneOf` でも `Value` プロパティから `object` として取り出すと、値型ケースをボックス化します。`Match` / `Switch` はケースごとのデリゲートを要求しますが、`null` を渡した場合は実行時エラーになり得ます。

もちろん、言語機能としての利点はあります。コンパイラーが Union を認識することで、`switch` 式の網羅性チェックや `u is int i` のような型パターンを使えます。`default` などで `null` の状態を取り得る Union では、その状態も考慮が必要です。また、System.Text.Json や OpenAPI が共通の形式を認識できます。ライブラリーでも個別に連携できますが、追加対応が必要になる場合があります。

言語仕様案は、既定の宣言を、一定の設計方針を採った簡潔な方式と位置付けています。値を 1 つの参照フィールドに収める一方で、値型はボックス化します。別の格納方式が必要なら、カスタム Union を選ぶ設計です。ボックス化しないレイアウトは、作業グループの検討資料で将来の選択肢として挙がっています。しかし、「出荷を約束するものではない」と明記されています。

値型のボックス化を避けたい場合は、既存の型付きライブラリーやカスタム Union との比較が必要です。さらに、System.Text.Json のソースジェネレーター経由ではケースを `object?` に変換するため、カスタム Union を選んでも JSON 化でボックス化し得ます。回避策はありますが、保持から利用まで一貫してコストを抑えるには、呼び出し側も意識しなければなりません。

C# には、ほかにも言語機能として解決してほしい課題があるのではないかと感じています。既定の宣言には値型をボックス化せず保持する選択肢がない現状では、Union を言語機能として追加する価値に、私はまだ納得できていません。

## ランタイム ― JIT・AOT・診断と実行環境の変更

JIT（実行時コンパイル）では、境界チェックや分岐の除去、非仮想化、定数入力に対する `SequenceEqual` の定数畳み込みなどを改善しています。

Native AOT（事前コンパイル）では、インターフェイス呼び出しに共有ディスパッチヘルパーを利用し、呼び出し箇所のコードサイズと実行時オーバーヘッドを改善しています。アプリケーションのコードを変更しなくても効果を受ける可能性がありますが、実際の効果は処理内容に依存します。

診断では、プロセス終了前にマネージドスタックやモジュールなどを記録する in-process crash report を Linux / macOS にも展開しています。コンテナーなど、障害発生後に情報を集めにくい環境で注目したい変更です。

一方で、**CPU 要件の変更**には注意が必要です。x86 / x64 向けの最低要件を `x86-64-v2` へ変更し、Windows / Linux の ReadyToRun コードのターゲットは `x86-64-v3` へ引き上げています。この 2 つは別の話で、`v3` が実行の最低要件になったわけではありません。Windows Arm64 では LSE が必須になります。

### Runtime Async は引き続きプレビュー

Runtime Async は、非同期処理をランタイム側で支え、性能や実行中の呼び出しスタックを改善する取り組みです。

.NET 11 の正式リリース後も、アプリケーションでの利用はプレビューです。`net11.0` では、次の設定で明示的に有効化します。

```xml
<PropertyGroup>
  <Features>runtime-async=on</Features>
</PropertyGroup>
```

ランタイムライブラリ側が利用していることと、アプリケーション側の新しいコンパイル方式が正式化したことは区別してください。また、実行中の live call stack の改善を、「例外スタックトレースが初めて読みやすくなる機能」と説明するのも正確ではありません。

## ASP.NET Core ― Union・非同期検証・OpenAPI・SignalR

### C# 15 の Union を Minimal API で使う

ASP.NET Core 11 の Minimal API では、C# 15 の Union を JSON の入力・出力に利用できます。例えば、検索条件を文字列またはオブジェクトで受け付けるような API を表現できます。

フレームワークが Union の形式を共通に扱えることは利点です。ただし、それによって既定の `union` の設計に対する私の疑問が解消するわけではありません。ボックス化や、後述する JSON・HTTP の扱いを確認したうえで、採用するか判断したいところです。

次は、Union の入出力と HTTP の結果を確認するためのサンプルです。`/search` は説明のため、受け取った値をそのまま返します。

```powershell
dotnet new webapi -n AspNetUnionDemo -f net11.0
Set-Location AspNetUnionDemo
```

`Program.cs` を次の内容に置き換えてください。OpenAPI の出力には `Microsoft.AspNetCore.OpenApi` が必要です。上記の .NET 11 の Web API テンプレートには含まれています。

```csharp
using Microsoft.AspNetCore.Http.HttpResults;

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddOpenApi();
var app = builder.Build();

app.MapOpenApi();
app.MapPost("/search", (SearchInput input) => input);
app.MapGet("/products/{id:int}", GetProduct)
    .ProducesProblem(StatusCodes.Status500InternalServerError);
app.Run();

static Results<Ok<Product>, NotFound, ProblemHttpResult> GetProduct(int id)
{
    ProductLookup result = FindProduct(id);
    return result switch
    {
        Product product => TypedResults.Ok(product),
        ProductMissing => TypedResults.NotFound(),
        null => TypedResults.Problem(
            detail: "Lookup result was not initialized.", statusCode: 500),
    };
}

static ProductLookup FindProduct(int id)
{
    if (id == 0)
        return default;

    if (id == 1)
        return new Product(1, "Keyboard");

    return new ProductMissing();
}

public sealed record SearchFilter(string Keyword, int Limit);
public union SearchInput(string, SearchFilter);
public sealed record Product(int Id, string Name);
public sealed record ProductMissing;
public union ProductLookup(Product, ProductMissing);
```

`dotnet run` で起動すると、次のように動作します。

| リクエスト | レスポンス |
|---|---|
| 🔎 `POST /search`、JSON の `"keyboard"` | 200、JSON の `"keyboard"` |
| 🔎 `POST /search`、JSON の `{"keyword":"keyboard","limit":10}` | 200、同じ形式の JSON オブジェクト |
| 📦 `GET /products/1` | 200、`{"id":1,"name":"Keyboard"}` |
| ❓ `GET /products/2` | 404、本文なし |
| ⚠️ `GET /products/0` | 500、未初期化状態を示すエラー |

`id == 0` は、ケースを持たない `default(ProductLookup)` の扱いを試すための分岐です。パターンマッチの `null` で検出し、500 を返しています。`ProblemHttpResult` のステータスは動的なため、ここでは `.ProducesProblem(500)` で OpenAPI のメタデータも明示しています。

`/openapi/v1.json` を確認すると、`SearchInput` のスキーマには、文字列と `SearchFilter` を表す **`anyOf`** が生成されます。`/products/{id}` のレスポンスには、200・404・500 が記載されます。OpenAPI の公開範囲は、実際のアプリケーションの運用方針に合わせてください。

### JSON を読み取るときの注意点

Union の JSON は、ケースを包むオブジェクトや型判別用の `$type` を自動で追加せず、ケースの値をそのまま表現します。読み取り時に複数のケースが同じ JSON に一致する場合は、どちらを選ぶか決められません。

例えば、Minimal API の既定の JSON 設定では、数値を JSON の文字列から読み取ることも許可されています。そのため `union(int, string)` に JSON 文字列を送ると、両方のケースに一致し得ます。実際に .NET 11.0.0 で試すと、数値の `42` は受け付けられますが、文字列の `"42"` や `"unknown"` は 400 になります。この組み合わせを入力に使う場合は、ケースを選択するカスタム classifier が必要です。

ケースが複数の JSON オブジェクトの場合は、プロパティ名による `JsonUnionTypeStructuralClassifier` も選択肢です。ただし、プロパティの変更で判別結果が変わる可能性があります。新規 API で契約を自由に決められるなら、closed 階層と明示的な discriminator を検討する方法もあります。

また、nullable なケースがない Union を JSON の `null` から読み取ると、ケースを持たない `default` になります。上の `SearchInput` でも `null` は `default` になり、サンプルは JSON の `null` を返します。受け入れる値の検証と、`default` の扱いを決めておきましょう。

この対応の基盤は System.Text.Json です。Minimal API だけでなく、MVC の JSON 入出力や SignalR の `JsonHubProtocol` にも利用できます。一方、Union の JSON サポートがルート、クエリ文字列、ヘッダー、フォームのバインディングにそのまま適用されるわけではありません。SignalR の MessagePack / Newtonsoft.Json プロトコルも、同じ Union 対応を持ちません。

### JSON の Union と HTTP の結果は別物

上の例では、`SearchInput` と `ProductLookup` が C# 15 の Union です。一方、`Results<Ok<Product>, NotFound, ProblemHttpResult>` は、以前から ASP.NET Core にある**型付き HTTP 結果**です。`ProductLookup` をパターンマッチし、HTTP 200・404・500 に明示的に変換しています。

ここで注意したいのは、`public union HttpResult(Ok<Product>, NotFound);` を宣言し、それを Minimal API から直接返しても、内部の `NotFound` が自動的に HTTP 404 として実行されるわけではないことです。

.NET 11.0.0 の既定の設定で確認したところ、`NotFound` を格納したその Union を直接返した場合、HTTP ステータスは 200 で、JSON の `{"statusCode":404}` が返りました。**JSON の中の `statusCode` と、実際の HTTP ステータスは別物**です。OpenAPI に 404 を追記するだけでも、実行時のステータスは変わりません。

この例のケースは `string` と `record` クラスなので、ケースの格納に伴う値型のボックス化はありません。ただし、Union 自体は struct です。ASP.NET Core やシリアライザーなどの汎用 API を通る処理まで含めて、割り当てやボックス化がゼロになることを保証するものではありません。

例えば、System.Text.Json のソースジェネレーターが作る Union の `UnionDeconstructor` は、ケース値を `object?` に変換します。前述のカスタム Union で値型を型付きフィールドに保持していても、JSON 化の経路でボックス化し得ます。JIT の最適化も含め、性能が重要な場合は実際のリクエスト経路で測定してください。

出典：[ASP.NET Core における Union の解説](https://devblogs.microsoft.com/dotnet/unions-and-closed-hierarchies-in-aspnetcore/?WT.mc_id=DT-MVP-5004827)、[System.Text.Json における Union](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/union-types?WT.mc_id=DT-MVP-5004827)、[JSON ソースジェネレーターの Union 実装](https://github.com/dotnet/runtime/blob/deae2e32bf0e018e09d64597b7c59b62b73bb3ce/src/libraries/System.Text.Json/gen/JsonSourceGenerator.Emitter.cs#L743-L789)

### Minimal APIs の非同期検証

`AsyncValidationAttribute` や `IAsyncValidatableObject` を利用して、非同期の入力検証を表現できます。`AddValidation()` で検証の仕組みを組み込む点も押さえておきましょう。

例えば DB への問い合わせが必要な検証でも、同期処理へ無理に押し込む必要を減らせます。ただし、事前検証で「重複なし」と判定しても、同時実行による競合は防げません。一意制約など、DB 側の整合性保証は引き続き必要です。

### OpenAPI 3.2 が既定に

OpenAPI ドキュメントの既定バージョンが 3.2 になります。SSE（Server-Sent Events）のイベントごとのペイロードを `itemSchema` で記述するなど、ストリーミング API の表現が広がります。

API クライアントの生成器やドキュメント表示ツールが、まだ 3.2 に対応していない場合もあります。その場合は `OpenApiVersion` で対応済みのバージョンを明示し、ツールチェーン全体で移行時期を決めるとよいでしょう。

### SignalR の認証更新とキャンセル

SignalR は、接続を切断せずに認証を更新できます。サーバー側では、ハブごとに `EnableAuthenticationRefresh` を有効化します。

通常の非ストリーミングのハブ呼び出しもキャンセルに対応します。長時間接続するアプリでは、トークンの期限と処理のキャンセルを、接続し直す前提だけで設計せずに済むようになります。

出典：[ASP.NET Core 11 の更新](https://learn.microsoft.com/en-us/aspnet/core/release-notes/aspnetcore-11?view=aspnetcore-11.0&WT.mc_id=DT-MVP-5004827)

## Blazor ― フォーム・キャッシュ・接続のライフサイクル

Blazor は、静的 SSR（サーバー側レンダリング）と対話型の両方で更新があります。どのレンダーモードの機能かを分けて見ると整理しやすくなります。

| 領域 | 主な更新 | 注意点 |
|---|---|---|
| 📝 静的 SSR フォーム | `DataAnnotationsValidator` を含むフォームでブラウザー側検証が既定で有効 | クライアント検証はサーバー側検証の代替ではない |

なお、Blazor の AI components は実験段階で、.NET 11 の期間を通じてプレリリースとして提供されます。通常の安定版コンポーネントと混同しないようにしましょう。

## EF Core 11 ― SQL 生成とモデル表現を改善

EF Core 11 は、.NET 11 SDK / ランタイムを必要とします。アプリケーションのターゲットと、使用する DB プロバイダーの対応バージョンを合わせて確認しましょう。

### クエリの翻訳と不要な SQL の削減

不要な参照ナビゲーションの JOIN や ORDER BY を取り除き、`GroupBy` の翻訳も改善しています。`MaxByAsync` / `MinByAsync` の翻訳や、対応する RDB での `FullJoin` から `FULL JOIN` への翻訳も加わります。

LINQ のコードが短くなったことと、SQL の実行コストが下がることは別です。移行時は、主要なクエリの生成 SQL と実行計画を確認してください。性能向上の数値を、そのまますべてのアプリケーションへ当てはめることも避けたいところです。

### Complex types と JSON の対応範囲を拡大

TPT / TPC の継承マッピングを利用するエンティティでも、complex types や JSON 列を利用できます。complex property 内のスカラー値を、キーやインデックスへ指定する機能も加わります。

complex types は、複数の値をひとまとまりとしてモデル化する仕組みです。継承や JSON 保存との組み合わせが広がり、モデルを保存先の制約へ合わせて分解する必要を減らせます。

### プロバイダー固有の更新

SQL Server では、全文検索のカタログとインデックスをマイグレーションから管理できます。Cosmos DB では、complex types、transactional batches、bulk execution などの対応を拡充し、内部の JSON 処理も System.Text.Json へ移行しています。

一方、SQL Server の vector index と近似ベクトル検索、および対応する EF API は実験段階です。全文検索の管理機能と、実験段階のベクトル検索機能をまとめて「正式対応」としないよう注意してください。

出典：[EF Core 11 の更新](https://learn.microsoft.com/en-us/ef/core/what-is-new/ef-core-11.0/whatsnew?WT.mc_id=DT-MVP-5004827)

## Desktop ― Windows Forms と WPF

### Windows Forms は新しい描画を opt-in で利用

Windows Forms は、`VisualStylesMode.Net11` によって新しい描画方式を明示的に選択できます。従来アプリが、更新だけですべて新しい描画へ切り替わるわけではありません。

**新しい描画方式とダークモードは独立した設定**です。ダークモードを有効化しただけで、`Net11` の描画になるわけではありません。また、コントロールによっては互換性のために従来の描画へフォールバックします。独自描画を含む画面は、実際の表示を確認してください。

自己完結型の発行では `ijwhost.dll` を含め、mixed-mode assembly を利用する際の起動失敗を防ぎます。WPF アプリでネイティブ連携を利用している場合は、通常の開発実行だけでなく、発行した成果物でも動作を確認したい変更です。

## .NET MAUI ― ランタイム構成と各プラットフォームの実装を更新

.NET MAUI では、各プラットフォームの既定ランタイムを CoreCLR へ揃えます。ただし、Apple の JIT を許可しない環境では、事前コンパイルとインタープリターを組み合わせます。「CoreCLR になったので、どの端末でも JIT を使う」という意味ではありません。

UI 側では、Windows の `CollectionView2` の既定化、Android Shell の handler ベースの実装への移行などがあります。対象端末で、表示・操作・ライフサイクルを含めて移行確認を進めましょう。

XAML Incremental Hot Reload はプレビュー、Android Native AOT は実験段階です。また、MAUI のサポート期間は .NET 本体とは別なので、.NET 11 の STS の期間をそのまま当てはめないでください。

出典：[GA 告知の .NET MAUI 更新](https://devblogs.microsoft.com/dotnet/announcing-dotnet-11/?WT.mc_id=DT-MVP-5004827)

## 移行時に確認したいこと

最初に SDK、ターゲットフレームワーク、NuGet パッケージ、実行環境を揃えます。開発端末だけでなく、CI、コンテナー、配布先のランタイムや CPU 要件も対象です。

| 確認対象 | 主な確認点 |
|---|---|
| 🔤 言語 | C# 15 の正式機能とプレビュー機能を分ける |
| 🔀 Union | 既存ライブラリーとも比較し、保持から JSON 化まで利用する経路の割り当てを測る |
| 🌐 Web | OpenAPI 3.2 に周辺ツールが対応しているか |
| 💾 データ | EF プロバイダー、生成 SQL、実行計画、マイグレーション |
| 🖥️ UI | Windows Forms の描画、WPF の発行成果物、MAUI の実機動作 |
| 🧪 実験機能 | Runtime Async やベクトル検索などを、意図せず有効化していないか |

新しい機能を一度にすべて採用する必要はありません。まず既存の処理を動かし、計測してから、割り当てや待ち時間など実際の課題に合わせて取り入れるのがよいと思います。

## おわりに

.NET 11 は、C# 15 の表現力に加え、ランタイム、CLI、Web、データアクセス、UI まで広く改善するリリースです。新機能を使うコードだけでなく、既存アプリケーションの実行や開発サイクルにも目を向けたい更新です。

特に Union は、コンパイラーやフレームワークとの連携が広がる重要な更新です。しかし、通常の `union` 宣言では値型ケースをボックス化します。値型をボックス化せず保持するライブラリーもある中、言語機能として導入する価値に、私はまだ納得できていません。

性能が重要な場合は、既存ライブラリーやカスタム Union と比較し、保持からシリアライズまで実際の処理経路で測定してください。回避策を紹介しましたが、それが既定の設計への疑問を解消するわけではありません。

それぞれの更新の利点と負担を見極め、正式機能とプレビュー機能を区別して取り入れていきましょう。🚀

## はじめに

20 年以上使ってきた PukiWiki のデータを残しながら、C# / .NET で動かすプロトタイプを作りました。PHP のコードを一行ずつ移したのではなく、データを引き継いで必要な機能を作る試みです。背景や設計については、[C# / .NET での PukiWiki 移行についてまとめた記事](https://qiita.com/tomokusaba/items/243ff98d696c677fbf34)に書いています。

長く使ってきたシステムには、ページの内容だけでなく、設定や記法、日々の使い方も染みついています。作り直すなら、コードだけでなく、そうした使い勝手もどう残すか考えたいところです📚

プロトタイプに取り組んだあと、生成 AI が開発の現場に入ってきました。そこで、**今なら PHP を捨てて別の言語へ移す以外の道もあるのではないか**と思うようになりました。

ただ、PHP の更新や PukiWiki の改修はまだ始めていません。私は PHP に詳しいわけでもありません。これから GitHub Copilot などの AI を使って調べ、PHPカンファレンス関西2026で共有できる材料を集めたいと思っています。

この記事では、実際の結果ではなく、**これから何を確かめたいのか**をお話しします。C# / .NET で作ったプロトタイプの経験と、これからの PHP の調査を混同しないようにします🧭

## C# / .NET で試したこと

私が作ったのは、PukiWiki のデータを引き継ぎ、C# / .NET で必要な機能を作るプロトタイプです。既存の PHP システムを本番で置き換えたわけではありません。当時は、PHP を更新する道とは別に、自分が扱いやすい C# / .NET で作り直す方法も試しました。

ここでいう移植は、PHP のコードを C# に翻訳することではありません。画面やページの記法、保存データ、普段の運用に欠かせない動きを見ながら、新しい実装で何を再現するか考える作業でした。仕様書にはなくても、いつの間にか定着した使い方があります。

作ってみると、言語を変えるだけでは済まないことが分かりました。元の動きを調べて互換性を確かめ、運用を切り替える準備も要ります。新しい言語を使っても、元のシステムを理解する手間は残ります。

この経験から「PHP を更新するより、別の言語へ移すほうがよい」とは言えません。当時は自分が実装や保守を続けやすいと考えて C# / .NET を選びましたが、PHP の更新とは同じ条件で比べていません。今度は、以前試さなかった道も見てみたいです。

そのために、まず PHP 側の現状を調べます。更新作業はまだこれからです🔎

## なぜ今、PHPへの進化を考えるのか

以前は、古い PHP アプリケーションを新しい環境に合わせるのは難しそうだと感じていました。バージョンごとの差や古いコードの意味、ライブラリ、実行時の挙動を調べ、変更の影響も確かめる必要があります。私は PHP を主な開発言語として使ってきていません。「先に PHP を勉強しなければ」と考えると、調査に取りかかるまで時間がかかりそうでした。

生成 AI にコードやエラーの説明、変更案やテスト案を尋ねれば、専門外の言語でも調べ始めやすくなるかもしれません。調査の助けになるなら、別の言語へ移すだけでなく、既存の PHP を少しずつ更新する方法も比べられそうです🤖

もちろん、AI に聞けば保守できると決まるわけではありません。提案されたコードが動いても、Wiki の仕様や使い方が保たれているとは限りません。説明がもっともらしくても、前提を取り違えていることがあります。

私が知りたいのは、コードの説明だけでなく、変更箇所を絞り、テスト結果を見て提案を判断するところまで AI が助けてくれるかです。元の仕様や使い方を、どこで自分が確かめるべきかも気になります。

比べたいのは「C# と PHP のどちらが優れているか」ではありません。PHP に詳しくない私が、AI の助けを借りて既存の PHP を保守・更新できるのか。自分の PukiWiki で試してみたいです📝

## 移植と PHP の更新をどう比べるか

「AI で PHP を直す」と言っても、何を見ればうまくいったと言えるのでしょうか。今のところ、私が気になっているのは次の点です。

| 観点 | これから確かめたい問い |
|------|------------------------|
| 🔎 コード理解 | 機能のつながりや、古いコードの役割をどこまで説明できるか |
| 🧰 変更 | 変更案の根拠や影響を、どこまで示せるか |
| 🧪 動作確認 | テスト案は、今までの使い方を確かめられる内容か |
| ⚖️ 方法選び | PHP の更新と C# / .NET への移植を、何を基準に比べるか |

まだ答えはありません。新しい PHP で起動したとしても、作業の手間や保守のしやすさ、既存機能との互換性までは判断できません。

比較する際は、対象にした機能や変更前の状態、どう動作を確かめたかも記録します。まず現状を見て、対象範囲とテスト方法を決めます。

「AI に助けてもらう」のと「AI に作業を任せる」のは違います。説明を読みながら進めるのか、変更まで頼むのかで、人が確認することも変わります。発表ではその違いも話せるよう、作業の過程を残します。

では、実際に試すならどこから始めるか。今考えている手順を紹介します。

## 発表までに試したいこと

まだ実施していない計画ですが、まず PukiWiki のデータや運用環境を壊さずに調べられる状態を作ります。準備ができたら、小さな範囲から試します。

### Step 1: 現在の状態と対象範囲を把握する

まずコードを変えずに、PukiWiki のバージョンや PHP の実行環境、設定、プラグイン、カスタマイズ、保存データ、普段使う機能を調べます。分かったことと、まだ分からないことを一緒に記録します。

20 年使ってきたからといって、全体を把握できているわけではありません。使っていない機能が残っていたり、小さなカスタマイズが日々の作業に欠かせなかったりするかもしれません。コードを見るだけでなく、自分が実際にどう使っているかも確かめます。

コードや設定を読むときは、ファイルの役割や関連する処理、依存関係を AI に尋ねてみます。ただし、答えに出てこなかった機能が「ない」とは限りません。コード検索や実際の使い方と照らし合わせます。

対象が大きければ、使われ方や変更の影響を見て、最初に調べる機能を絞ります。範囲を明らかにしておけば、何を確かめたのかも伝えやすくなります。

### Step 2: PHP 環境で見える課題を切り分ける

次に、対象の PHP バージョンと実行条件を決めてコードを動かします。どのバージョンにするかは、公式情報と環境を調べてから決めます。発表では、調べた時点や選んだ理由も添えます。

起動時にエラーや警告が出たり、拡張機能やライブラリの条件が変わったりするかもしれません。表示をそのまま消すのではなく、原因と変更の影響を調べます。エラーが出なくても、機能が正しく動くとは限りません。

AI には答えだけでなく、根拠や確かめ方も聞きます。「この警告を消すコードを書いて」と頼むだけでは、原因を見落とすかもしれません。提案の前提や参照した公式資料、変更後に試すテストを見て、自分で採用するか決めます。

### Step 3: AI に調査と変更をどこまで任せられるか試す

コードの説明、調査の進め方、変更案の作成は、別々に頼んで記録します。いきなり大きく変えると、どの提案が役立ったのか見えにくくなるからです。変更する場合は小さく直し、差分を読んでから動かします。

コードだけでなく、AI への指示や前提、参考情報、提案を採用したか、どう確かめたかも残します。「AI が直した」だけで済ませず、作業の中身を説明するためです。使うツールやモデル、任せる範囲は、試す前に決めます。

わざと曖昧な指示を出したり、本番環境に危険な変更を加えたりはしません。安全に試せる環境やデータのコピー、変更を戻す方法を用意できなければ、実データは触らず、コードを読むところまでにします。

### Step 4: 既存の使い方を基準に動作を確かめる

変更したら、どの機能をどんな入力で試し、前後で何が変わったかを記録します。ページ表示や既存データ、使っている記法やプラグインのうち、何を試すかは現状を調べてから決めます。

自動テストを通っても、使い方が保たれたとは限りません。テストした範囲と、していない範囲を分けて伝えます。新しいテストを作るときも、その期待値が元の仕様や使い方に合っているか見ます。

AI にテスト案を出してもらうことも考えています。ただ、今の実装に合わせたテストでは、間違った動きを正しいものとして残すかもしれません。何を守るテストなのか、自分で説明できるかを確かめます。

### Step 5: C# / .NET への移行と比べる

最後に、PHP 側で試したことを、以前の C# / .NET のプロトタイプと並べて振り返ります。同じ条件で作業時間や工数を測ったわけではないので、単純な数字の比較はできません。個人的な感想と、確かめた事実は分けて話します。

見るのはコードの変更量だけではありません。元の仕様を理解する手間や、データとの互換性、今後自分で保守できるか、運用を切り替えるリスクも気になります。移植すれば新しい実装を自分で管理できますが、機能を再現して保守し続けることになります。PHP を更新するなら今の運用を活かせるかもしれませんが、コードを理解して更新に追いつく必要があります。どちらが自分に合うか、実際に調べて考えます。

PHP を更新するか、別の言語へ移すか。最初から二択に決めなくてもよさそうです。一部だけ別の方法にする案も含め、調べて分かったことをもとに考えます。

## AIに任せたいこと、人が判断すること

AI に何を頼み、どこから自分で確かめるのか。今の私なりに役割を分けてみました。

| 作業 | AI に頼みたいこと | 私が確かめること |
|------|------------------|------------------|
| 🗺️ コードの把握 | ファイルや処理の関係を整理する | 説明がコードや実際の使い方に合うか |
| 🧩 変更案 | エラーや警告への対応案を出す | 変更の目的と、機能への影響 |
| 🧪 テスト | 入力や確認項目を提案する | テストが守りたい使い方を確かめているか |
| 📝 作業記録 | 差分やログをまとめる | 実行したことと確認できたこと |
| 🚦 適用判断 | リスクや未確認点を挙げる | 実運用に使えるか、元に戻せるか |

これは試す前の見立てです。AI が調査を助けてくれるかもしれませんし、前提を伝えきれず、かえって確認に手間取るかもしれません。回答だけでなく、私が確かめたことも残します。

この Wiki をどう使ってきたかは、私にしか分からないこともあります。コードに書かれていない習慣や期待を AI が知っているはずはありません。一方で、当たり前になりすぎて、私自身が言葉にできない使い方もありそうです。何を残したいのか、まず自分に問い直す必要があります。

AI に作業を頼んでも、最後に採用するか決めるのは私です。うまくいった変更だけでなく、採用しなかった提案や説明を調べ直した場面も、発表では紹介したいと思います。

## この記事でまだ言えないこと

新しい PHP 環境での動作確認は、まだ始めていません。対象のバージョンや出てくるエラー、必要な修正も分かっていないため、移行できたか、互換性や保守のしやすさがどう変わるかは、これから確かめます。AI の正答率や作業時間も、実際に記録してからでなければ語れません。

これは「AI があれば PHP の知識はいらない」という話でも、「C# / .NET を選んだのは間違いだった」という話でもありません。AI の助けを借りることで、以前は選びにくかった方法を比べられるのか。PHPカンファレンス関西2026では、その過程と分かったことを共有したいです。

## PHPカンファレンス関西2026で一緒に考えたいこと

PHPカンファレンス関西2026で発表できたら、完成した手順だけでなく、C# / .NET のプロトタイプを作った私が、なぜ今 PHP の更新を考えているのかもお話ししたいです。分かったことも、分からなかったことも、そのまま共有します。

みなさんにも聞いてみたいことがあります。

- AI は、長年使われてきたコードの「今の状態」をどこまで理解できるのか
- 変更候補の説明や実装を任せるとき、どの証拠を確認すれば安心できるのか
- テストが足りないシステムで、AI が生成したテストをどう評価すればよいのか
- 保守経験が少ない言語に対して、AI はどの作業を助け、どの知識の不足を埋められないのか
- 更新と移植のどちらを選ぶかを決めるとき、開発者は何に責任を持つべきなのか

どのシステムにも同じ答えが当てはまるわけではありません。規模や利用者、データ、運用体制、保守する人が扱える技術によって方法は変わります。AI の一般論ではなく、長く使ってきたシステムで私が何を確かめたかを話したいです。

私は PHP の専門家ではありません。だからこそ、専門外の言語を扱うときに AI の説明をどう使い、何を自分で調べるのかを試します。詳しい方に聞いてみたいことも出てくると思います。そうした疑問も率直に話せる発表にしたいです🎤
